# Assumptions

Decisions made without stopping to ask, per the project brief's "don't stop unless truly blocked" rule.

1. **Package versions** (checked against npm registry on 2026-11-05): Phaser 3.90.0, Capacitor 8.0.3, Vite 8.0.5, Vitest 4.0.6, TypeScript 5.9.3, @supabase/supabase-js 2.75.0.
2. **Billing library**: `cordova-plugin-purchase` is the most actively maintained Capacitor-compatible Play Billing wrapper at time of writing (supports Billing Library 7+, consumables). Wired in Phase 6.
3. **Min/target/compile SDK**: min 24, target/compile = latest required by Play for new apps at time of writing (34+; the Android workflow pins the exact numbers — check `android/variables.gradle` once Phase 1 finishes, since Google's requirement changes yearly).
4. **Local toolchain**: this machine has Node/npm/git only — no `gh` CLI, no Java/Android SDK, no `adb`, and the GitHub MCP connector failed to authenticate. GitHub Actions supplies its own JDK 21 + Android SDK, so CI builds are unaffected. Creating the GitHub repo and the first push need one decision from you — see the open question in chat.
5. **Hinglish strings**: written in Roman-script Hindi transliteration by me (not a native-speaker review); flag any that read oddly and I'll adjust.
6. **Art**: all original SVG, generated in this repo — gradients/shapes described in-code, not traced from any existing game's assets.
7. **Audio**: Phase 7 implements `SoundService` with a documented list of filenames to supply, since I cannot legally source or generate finished music/SFX files inside this environment; placeholders are silent.
8. **Anonymous auth + optional Google linking** per spec section 6; Google Sign-In stays behind `ENABLE_GOOGLE_SIGNIN` (default false) until you complete its Play Console / Google Cloud setup (MANUAL_STEPS.md).
9. **Keystore**: I generate a *local test* keystore only for CI secrets I control (none — a release keystore must be generated and held by you; I will never generate or hold a Play App Signing keystore for you). See MANUAL_STEPS.md.
10. **Toolchain versions discovered by trial in CI** (document for future phases): `@capacitor/cli@8.6.0` requires Node ≥22 (the workflows originally pinned 20), and Capacitor's Android module compiles against Java 21 source/target (the workflows originally pinned JDK 17, which fails with "invalid source release: 21"). Both fixed in commit `2a27543`'s follow-up.
11. **The 50 levels are generated + validated, not individually hand-tuned by a designer.** `scripts/generate-levels.mjs` parametrizes the difficulty curve from section 3.5 (tutorial 1-5, ice from 6, more ice/locked from 11, locked from 16, ice+locked+honey mix from 20) and every level passes `validateLevel()` (board has no pre-existing match, has a legal move, goals are reachable within the move budget). Difficulty *feel* — whether level 23 is actually harder than level 22 in practice — hasn't been human playtested; treat the curve as a solid starting point to retune by hand-editing the JSON files (no code changes needed) once you've played through them.
12. **Blocker mechanics are simplified** versions of the spec, not exact Candy-Crush-style behavior (which isn't fully specified anywhere I could check): ice1/ice2 live on the tile itself and absorb one match each; locked "rock" tiles have no sweet and clear when any orthogonally adjacent match fires; honey spreads to exactly one random neighbor per swap it survives (not a tuned rate). See the `shortcut:` comments in `src/core/cascade.ts`.
13. **Life-spend timing**: the brief says both "starting a level costs 1 life" and "losing a level loses the life... life is spent on a failed level" — those can't both be literally true. I took the explicit "keep it simple: life is spent on a failed level" sentence as the tiebreaker: a life is deducted only when a level attempt ends in a loss, not when it starts.
14. **Pre-level boosters auto-apply**: Extra Striped / +3 Moves are consumed from inventory (1 of each, if owned) the instant "Start" is tapped in the pre-level popup, rather than a separate toggle — simpler UI, same net effect.
15. **Out-of-lives "Buy 5 lives (IAP)"** is a visible, honest placeholder in Phase 4 ("coming soon") rather than a fake purchase — real Google Play Billing lands in Phase 6 and will replace it.
16. **Hinglish strings** cover the menu, map, shop, settings, daily reward and pre-level popup — the core gameplay HUD (Level/Moves/Score/goal text, win/fail popups) still shows English words, since `GameScene` was built in Phase 3 before the i18n file existed. Retrofitting it is a quick follow-up (swap the literal strings for `t('...', lang)`), flagged here rather than silently left undone.
17. **No live Supabase project exists yet.** Creating one is a billing-adjacent action my environment blocks without your explicit approval (even at $0/month) — see MANUAL_STEPS.md Phase 5 §1. I wrote and locally reasoned through the full schema, RLS policies, RPC functions, and Edge Functions, but **none of it has run against a real database**, so treat it as carefully-written-but-unverified until you approve project creation (or create one yourself) and I can apply the migrations and actually test them.
18. **Client-side Supabase wiring is partial by design, not oversight.** `src/services/cloudSync.ts` does anonymous sign-in + a one-time profile merge on boot, and pushes `complete_level`/`claim_daily_reward` to the server best-effort (local storage stays the source of truth either way). Spend/grant-coin, booster use, and shop-purchase call sites are **not** yet also calling their matching RPCs (`spend_coins`, `buy_booster`, `buy_decoration`, etc.) — those RPCs exist and are written, just not wired into every client call site. Wiring the rest in without a live project to test against would be guessing at correctness; flagging it here instead of claiming "full sync" that I haven't verified.
19. **`.env.local` is never committed** (gitignored) and nothing in this repo requires Supabase to work — every scene, test, and the debug APK build run identically whether or not `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are set.
20. **`RealBillingProvider` is written against `cordova-plugin-purchase`'s documented API but is device-unverified** — there's no Play Console access or physical device signed into a license-test account in this environment to actually exercise it. `MockBillingProvider` (used automatically outside production builds) IS verified end-to-end in-browser: buying a coin pack credits coins instantly, and the full out-of-moves "Continue with coins" flow was exercised and confirmed to preserve the board exactly. Typed loosely (`window.CdvPurchase` as a structural `any`-backed interface) rather than importing the plugin's ~7000-line ambient `.d.ts` — tighten once you can test on a real device.
21. **`continue_moves_5` has no server-side coin/life grant** — `apply_purchase()`'s idempotency (the `purchases` row + unique `purchase_token`) still records and protects it from double-grant, but the actual "+5 moves" effect is applied entirely client-side once `verify-purchase` reports `granted: true`, per the spec's own looser wording for this one product ("signed grant" was simplified away — see `verify-purchase/index.ts`'s comment).
22. **The out-of-moves "Get coins" shortcut** opens the Store as a paused overlay scene (`scene.pause()` / `scene.launch('Store', { overlay: true })`) rather than navigating away, so the frozen board is never torn down — verified this preserves state exactly when returning.
23. **MockBilling's code ships in the production bundle** (Vite doesn't prove `USE_MOCK_BILLING` is statically `false` well enough to tree-shake the class out), but it is never *instantiated* in a production build (`billing/index.ts` picks `RealBillingProvider` whenever `import.meta.env.MODE === 'production'`, which `android-release.yml`'s `--mode production` always sets) — functionally equivalent to "excluded," just not byte-for-byte absent from the APK. Not worth a build-time conditional-import setup for a ~340 KB gzipped bundle.
24. **Audio files don't exist** — I can't legally source or generate finished music/SFX in this environment. `src/services/sound.ts` is a real, wired `SoundService` (every gameplay/UI event calls `sound.playSfx(...)`, respecting the Settings sound toggle) that is currently silent because there's nothing to play; `REQUIRED_AUDIO_FILES` in that same file lists the exact filenames to drop into `src/assets/audio/` to make it real, with no other code changes needed beyond the one `TODO` comment inside `playSfx`/`startMusic`.
25. **Haptics are real, not a placeholder** — `src/services/haptics.ts` calls `@capacitor/haptics` directly (light impact on swaps/buttons/boosters, success/error notifications on win/fail), respecting the Settings vibration toggle. It no-ops harmlessly outside a native app (desktop browser), which is how I verified it doesn't throw.
26. **Object pooling (spec 3.11's performance guidance) was not implemented.** `GameScene` destroys and recreates every tile container on each cascade step (`renderFullBoard`) rather than diffing and reusing sprites — simpler and already tested working, but not the pooled-sprite approach the spec mentions for best performance on mid-range devices. On an 8x8-9x9 board this is at most ~81 Phaser Image objects recreated per step, which should be fine on a mid-range device, but it's a real simplification worth revisiting if profiling on a real device shows jank during long cascades.
27. **No real device/emulator performance profiling happened** (60fps, cold-start-under-3s targets) — there's no Android device or emulator in this environment. The debug APK is confirmed to build, install-sideload-able, and runs the full gameplay loop correctly in the Chromium-based preview used throughout this project, but actual on-device frame timing is unverified.
